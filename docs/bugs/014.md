# Bug 14 — Full-text search materializes up to 500 full documents in memory per query

**File:** `neoblogger/app/repositories/articles.py`
**Severity:** MEDIUM (performance)

## Description

In `ArticleRepository.search()` (`neoblogger/app/repositories/articles.py:176-200`), every search query materializes up to `_MAX_SEARCH_CANDIDATES = 500` full article documents (including `body`) into a Python `list`, then slices `candidates[start : start + per_page]` in application code:

```python
# neoblogger/app/repositories/articles.py:188-198
cursor = (
    connection.articles.find(query)
    .sort([("score", {"$meta": "textScore"})])
    .limit(_MAX_SEARCH_CANDIDATES)
)
candidates = list(cursor)
if not candidates:
    return [], 0
start = (page - 1) * per_page
window = candidates[start : start + per_page]
return [_normalize(document) for document in window], len(candidates)
```

## Impact

- A search matching 500 articles loads, deserializes from SQLite JSON, and allocates 500 full article dicts (including multi-kilobyte `body` fields) on every single page view, only to return 10 items.
- Because search responses are never cached ([Functional Requirements](../requirements.md) §9, §14), repeated search requests pay this 500-document materialization cost on the single-threaded DB executor every time.

## Suggested Fix

- Exclude `body` from search result documents (`projection={"body": 0}`) since `_feed_cards.html` only renders `title`, `subtitle`, `cover_url`, `tags`, `author`, and `created`.
- Use cursor pagination (`.skip(start).limit(per_page)`) plus `count_documents(query)` (bounded or exact) inside the executor work unit so only `per_page` documents are deserialized into Python dicts.
