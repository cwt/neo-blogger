# Bug 19 — $O(N)$ per-member `update_many` loop at startup in `backfill_author_snapshots`

**File:** `neoblogger/app/repositories/db.py`
**Severity:** LOW (performance / algorithm)

## Description

`backfill_author_snapshots()` (`neoblogger/app/repositories/db.py:159-178`) runs on every worker startup and iterates through every member in `connection.members.find({})`, issuing an unconditional `articles.update_many` query for each member:

```python
# neoblogger/app/repositories/db.py:167-175
for member in list(connection.members.find({})):
    snapshots = {
        "author_active": bool(member.get("active", False)),
        "author_publisher": bool(member.get("publisher", False)),
    }
    result = articles.update_many(
        {"author": member["display_name"]}, {"$set": snapshots}
    )
    changed += result.modified_count
```

Even when 99% of registered members have written zero articles or their snapshots are already in sync, every Gunicorn worker runs $N$ separate `update_many` statements on startup.

## Impact

- Startup time scales linearly with total registered members ($O(N)$ queries per worker) rather than with the number of distinct authors whose snapshots actually differ.

## Suggested Fix

- Filter only to distinct authors present in `articles` (and `comments`, per [Bug 4](004.md)), or add a `$or` mismatch predicate (`{"author": name, "$or": [{"author_active": {"$ne": active}}, {"author_publisher": {"$ne": publisher}}]}`) so `update_many` only touches out-of-sync rows.
