# Bug 13 — Listing queries, `/profile`, and `/sitemap.xml` fetch full article `body` content unnecessarily

**Files:** `neoblogger/app/repositories/articles.py`, `neoblogger/app/blueprints/profile.py`, `neoblogger/app/blueprints/seo.py`
**Severity:** MEDIUM (performance)

## Description

1. **Unprojected `body` in listing queries (`neoblogger/app/repositories/articles.py:139-174, 294-304`):**
   - `feed_page()` (`articles.py:139-164`), `for_author()` (`articles.py:166-174`), `search()` (`articles.py:176-200`), and `unpublished_review()` (`articles.py:294-304`) fetch complete article documents including the full `body` Markdown string.
   - None of the listing templates (`_feed_cards.html`, `profile.html`, `review.html`) or `/sitemap.xml` ever access `article.body`.
   - On `/sitemap.xml` (`neoblogger/app/blueprints/seo.py:66-74`), `feed_page()` fetches batches of `_SITEMAP_PAGE_SIZE = 1_000` full articles (with multi-kilobyte `body` strings) when only `_id` and `created` are used.

2. **Unbounded full-collection scan per author on `/profile` (`neoblogger/app/blueprints/profile.py:24-27`):**
   ```python
   # neoblogger/app/blueprints/profile.py:23-27
   stats = await context.accounts.profile_statistics(g.member)
   posts = await context.visibility.articles_by_author(g.member["display_name"])
   drafts = [post for post in posts if post["status"] == "draft"]
   published = [post for post in posts if post["status"] == "published"]
   recent_published = published[:_RECENT_PUBLISHED_LIMIT]
   ```
   Although `profile_statistics()` carefully comments *"Counts run in the engine; article bodies are never loaded (§14)"* (`neoblogger/app/services/accounts.py:167`), the very next line in `profile.py` calls `articles_by_author()`, which loads **every article the author has ever written (including full `body` text)** into Python memory just to filter `drafts` and slice the first 5 `published` posts (`_RECENT_PUBLISHED_LIMIT = 5`).

## Impact

- High memory allocation and JSON deserialization overhead on every feed, tag, search, profile, review, and sitemap request as article count and body lengths grow.
- For prolific authors (e.g. hundreds of long-form articles), `/profile` transfers and deserializes all historical article bodies on every page load, discarding all but 5 published rows.

## Suggested Fix

- Project out `body` (`{"$project": {"body": 0}}` or `projection={"body": 0}`) in listing queries (`feed_page`, `for_author`, `unpublished_review`, `search`) or provide a dedicated `sitemap_entries()` query projecting only `{"_id": 1, "created": 1}`.
- On `/profile`, query drafts and the 5 most recent published articles (plus counts) in a single `$facet` aggregation pipeline (backed by the existing `(author, status, created DESC)` compound index) with `{"$project": {"body": 0}}`.
