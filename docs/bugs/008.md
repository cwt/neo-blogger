# Bug 8 — Password recovery double-counts rate limit attempts and misreports empty answer / password errors

**Files:** `neoblogger/app/blueprints/auth.py`, `neoblogger/app/services/accounts.py`
**Severity:** MEDIUM

## Description

In `neoblogger/app/blueprints/auth.py:107-147`, the `/recover` route handles both Step 1 (looking up the email to display the member's security question) and Step 2 (verifying the security answer and setting `new_password`) in the same `POST /recover` handler:

```python
# neoblogger/app/blueprints/auth.py:113-147
if request.method == "POST":
    form = await request.form
    email = form.get("email", "").strip()
    if not recovery_limiter_allow(
        request_client(context.proxy_trust), email.lower()
    ):
        await flash("Too many attempts. Try again later.", "error")
        return redirect("/recover")
    ...
    question = QUESTION_LABELS.get(member["security_question_code"])
    if form.get("answer"):
        ...
        if ok:
            await flash("Password reset. You can now sign in.", "success")
            return redirect("/signin")
        await flash("The answer did not match. Try again.", "error")
return await render_template("recovery.html", email=email, question=question)
```

This causes three issues:

1. **Double rate-limit consumption:** A single legitimate password recovery requires two `POST /recover` requests (Step 1 with `email` only; Step 2 with `email`, `answer`, and `new_password`). Both increment the same 5-attempt window in `_recovery_limiter`, so a user gets at most 2 actual answer attempts before being locked out.
2. **Silent no-op on empty `answer` in Step 2:** Because Step 2 is detected via `if form.get("answer"):` (truthiness check instead of `"answer" in form`), submitting Step 2 with an empty `answer=""` skips the `if` block entirely and re-renders `recovery.html` with 200 OK and no error message.
3. **Misleading error when `new_password` is empty or short:** In `AccountService.recover()` (`neoblogger/app/services/accounts.py:117-121`), `if not new_password: return False` returns the same `False` sentinel as a wrong security answer, causing `auth.py:146` to flash `"The answer did not match. Try again."` even when the answer was correct.

## Impact

- Users attempting password recovery exhaust 2 of 5 rate-limit tokens on their first try.
- Submitting an empty answer or empty password produces either no feedback or an inaccurate error message, and returns a 200 response to a `POST` that triggers browser form-resubmission warnings on refresh.

## Suggested Fix

- Detect Step 2 via `"answer" in form` (or a hidden `step` input).
- Validate `answer.strip()` and `new_password` explicitly with clear error messages before calling `verify_secret`.
- Count rate-limit attempts once per recovery step or separate Step 1 lookup limiting from Step 2 answer verification limiting.

**Status:** Fixed (see [Bug Tracker](index.md)).
